문제설정 없이 쓰는 LLM

LLM은 이 프로젝트를 매번 처음 보는 셈입니다

매번 설명을 다시 쓰는 것도 일이지만, 설명이 빠져 엉뚱하게 나온 코드를 되돌리는 게 더 큰 일이죠.

컨벤션이 조금씩 무너져요

같은 기능인데도 어떤 파일은 Service에서 트랜잭션을 열고, 어떤 파일은 Controller에서 엽니다. 리뷰에서 걸러지지 않으면 그대로 굳어 버리죠.

영향 범위가 잘 안 보여요

메서드 하나를 고쳤을 뿐인데 배치와 화면이 같이 멈추기도 합니다. 호출 관계가 코드 속에만 있고, 어디에도 정리돼 있지 않으니까요.

장애가 나면 사람부터 찾아요

원인 코드를 찾는 시간보다 "이거 지금 누가 맡고 있죠?"를 확인하는 시간이 더 길 때가 많습니다. 담당자 정보가 사람 머릿속과 여기저기 흩어진 문서에 나뉘어 있거든요.

세 가지 모두 결국 "이 시스템에 대한 지식이 코드 밖에 정리돼 있지 않다"는 한 가지 원인에서 나옵니다. Total ITO는 그 지식을 한 번 만들어 두고 계속 재사용하는 형태로 바꿔 줍니다.
전체 그림한 번 분석 → 계속 재사용

지식을 파일로 남겨 두고, 작업할 때마다 그걸 다시 읽습니다

설치개발자 PC · 최초 1회

명령 두 줄이면 끝나요

마켓플레이스를 등록하고 플러그인을 설치하면 됩니다. 프로젝트마다 다시 할 필요는 없어요.

# 1단계 — 마켓플레이스 등록 (최초 1회)
/plugin marketplace add Malburi/total_ito
# 2단계 — 플러그인 설치
/plugin install total-ito@total-ito
# 3단계 — 확인
/plugin list
total-ito@total-ito — enabled ✓
터미널에서 비대화형으로 설치하려면 claude plugin install total-ito@total-ito --scope user를 쓰세요. 설치가 안 되면 저장소 루트에서 claude plugin validate . --strict로 원인부터 확인해 보시고요.

설치되는 것

스킬 17종 — 자연어 요청을 받아 절차를 실행하는 워크플로우
에이전트 19종 — 분석·판정·생성을 나눠 맡는 역할
스크립트 — 인덱싱·검증·위키·DB 발행 (LLM 호출 없음)

설치되지 않는 것

대상 시스템의 소스는 그대로예요. 분석 결과 파일이 생길 뿐이고, 그것도 다음 단계에서 직접 실행할 때 만들어집니다.

필요한 준비물

Claude Code 최신 버전이면 됩니다. 중앙 DB 발행까지 쓸 계획이라면 파이썬 패키지 sqlalchemy와 DB 드라이버 하나만 더 준비하세요.

왜 구성을 먼저 묻나요

백엔드와 프론트엔드가 다른 저장소라면 분석 범위도, 나중에 위키를 묶는 방식도 달라집니다. 여기서 잘못 잡으면 한 시스템이 둘로 쪼개져 보이거든요.

기본값이 Full인 이유

레거시 유지보수에서는 얕은 분석이 놓친 위험(미해결 관계·인증 우회·트랜잭션 경계)을 나중에 치르는 비용이 분석 시간보다 큽니다. 그래서 범위를 줄이는 쪽은 한 번 더 여쭤봐요.

Standard

3~5분

Full · 기본

git에 커밋할 것

CLAUDE.md 와 .claude/ 예요. 팀원이 이걸 받으면 그 사람의 Claude도 똑같은 컨벤션과 도메인 지식으로 시작합니다. "한 사람이 분석하고 팀이 재사용한다"가 실제로 이런 모습이에요.

남겨두면 좋은 것

_workspace/index/ 는 영향도 분석과 안전 변경이 참조하는 파일이에요. 지우면 그 작업들이 코드를 처음부터 다시 훑어야 해서, 느려지고 토큰도 더 씁니다.

코드가 바뀌면

전체를 다시 초기화할 필요 없이 "인덱스만 갱신해줘"라고 하면 됩니다. 바뀐 파일만 증분으로 분석해요 — LLM 호출 없이 수십 초면 끝납니다.

분석 결과_workspace/index/*.json

코드에 흩어진 관계를 질의할 수 있는 형태로 바꿔 둡니다

전부 결정적으로 뽑아냅니다 — 같은 소스를 넣으면 늘 같은 JSON이 나오고, 만드는 데 LLM을 쓰지 않아요.

call_graph

어떤 함수가 어떤 함수를 부르는가

symbols

클래스·메서드가 어디 있는가

sql_usage

SQL ID ↔ 호출 위치

transactions

트랜잭션이 어디서 열리고 닫히는가

schema

테이블·컬럼 구조

data_flow

데이터가 흐르는 경로

api_contract

엔드포인트와 요청·응답

ui_flow

화면 전환과 진입점

client_index

JS ↔ JSP 매핑 (레거시 정적 JS)

external_io

외부 시스템 연동 지점

env_branches

환경별로 갈리는 코드

dead_code

아무도 부르지 않는 코드

_meta — 어디까지 믿을 수 있는가

파일마다 FULL PARTIAL UNSUPPORTED 를 기록해요. WinForms Designer · DevExpress · XFDL · JSP/Struts XML 처럼 PARTIAL인 대상은 자동 변경 판정이 HOLD로 고정됩니다 — "파일을 찾았다"를 "안전하게 고칠 수 있다"로 부풀리지 않으려는 장치예요.

활용초기화 이후

명령을 외울 필요 없이 — 평소 하던 말을 그대로 하면 됩니다

코드 이해

"주문 취소 로직 어떻게 돼?"

trace-logic → 진입점 · Controller · Service · Repository · 실제 실행되는 SQL까지 한 줄로 이어 붙인 흐름 리포트

코드 위치

"결제 관련 코드 어디 있어?"

find-feature → 관련 파일 · 클래스 · 메서드 · SQL ID 목록. 키워드가 코드에 없어도 도메인 지식으로 찾는다

변경 전 확인

"OrderService.cancel 고치면 어디 영향가?"

analyze-impact → 직접 호출자 · 트랜잭션 경계 · 관련 테스트 · 영향받는 화면

안전 변경

"이 변경 안전하게 적용해줘"

safe-modify → 영향 분석 → 기준 패턴 선택 → 적용 → 패턴 적합성·빌드 검증 → GO / HOLD / STOP 판정

신규 개발

"환불 기능을 컨벤션에 맞게 만들어줘"

scaffold-feature → 기존 패턴을 골라 Controller · Service · Repository · DTO · 테스트 골격을 한 번에

SQL 리뷰

"이 쿼리 문제없어?"

review-sql → 사용처 · 인덱스 활용 · N+1 위험 · 인젝션 · DDL 영향

마이그레이션

"Oracle에서 PostgreSQL로 전환 계획 짜줘"

plan-migration → 인벤토리 → 매핑 표 → 단계별 계획 → 리스크 레지스터 → 롤백 플랜

알아서

"알아서 해줘"

vibe → 사소한 작업은 빠르게 끝내고, 위험한 변경이라고 판단되면 스스로 safe-modify 절차로 승격한다

활용 시나리오운영 중 장애

장애가 난 순간부터 조치안까지, 같은 창 안에서

왜 빠른가요

코드를 처음부터 훑지 않아요. 미리 만들어 둔 호출 그래프·SQL 사용처·트랜잭션 경계 인덱스를 먼저 질의해 후보를 좁힌 다음, 그 파일만 읽습니다.

상황을 말해 주면 기준이 달라져요

운영 패치야 긴급 핫픽스야 레거시 손보는 거야 고객 데모 직전이야 — 상황에 맞춰 안전성 판단의 무게추가 함께 옮겨 갑니다.

활용safe-modify 판정

고친 다음, 한 번 멈춰 세우는 단계가 있어요

변경을 적용했다고 끝이 아닙니다. 적용 결과를 다시 평가해 세 가지 중 하나로 답해요. 어떤 경우에도 자동으로 밀어붙이지 않습니다.

GO

진행해도 괜찮아요

영향 범위가 닫혀 있고, 선택한 기준 패턴과도 어긋나지 않으며, 최소 검증(빌드·테스트)까지 통과한 경우예요.

HOLD

확인이 좀 필요해요

영향은 파악됐지만 아직 검증하지 못한 구간이 남아 있습니다. PARTIAL 지원 스택(WinForms Designer · XFDL 등)이 걸린 변경은 여기서 멈춰요. 무엇을 확인해야 하는지 함께 알려 드립니다.

STOP

이 방식은 권하지 않아요

트랜잭션 경계를 넘거나 인증 경로를 우회하는 등, 지금 방식으로는 위험이 남는 경우예요. 대안을 함께 제시하고 논의로 넘깁니다.

이 구조가 있어야 "LLM이 알아서 고쳤는데 뭘 고쳤는지 모르겠다" 같은 일이 안 생겨요. 판단은 언제나 사람이 합니다 — 도구는 판단에 필요한 재료를 빠짐없이 모아 올 뿐이고요.
활용백엔드와 프론트엔드가 따로 있을 때

저장소가 나뉘어 있어도 계약으로 이어 붙입니다

"양쪽 다 수정해줘"

cross-repo-modify — API 시그니처가 바뀌는 변경을 양쪽 저장소에 맞춰 반영해 주고, 계약이 어긋나면 그 지점을 짚어 줍니다.

"전체 스택 기능 만들어줘"

cross-repo-scaffold — 백엔드와 선택한 클라이언트에 신규 기능 골격을 동시에 만들어요. 허브형 1:N(웹+모바일+관리자)도 지원합니다.

위키에서는 한 시스템으로 묶여요

저장소가 둘이어도 시스템 키만 같으면 중앙 위키에서는 한 시스템 아래 두 레이어로 보입니다. 이 규칙이 깨지면 한 시스템이 둘로 쪼개져 버려요.

위키generate-wiki

분석 결과를 사람이 읽는 문서로 바꿔 줍니다

이미 만들어 둔 인덱스와 리포트를 조립하는 단계라 LLM을 거의 쓰지 않아요 — 몇 번을 돌려도 결과가 같습니다.

.env에 한 번 저장해 두면 다음 발행부터는 묻지 않아요. .env는 git에 커밋하지 않으니 개인 정보가 저장소로 샐 일도 없습니다.

담당자 정보는 선택이에요

아무것도 안 남기면 담당자 없이 그대로 발행돼요 — 강제로 묻지 않습니다. 남기기로 했다면 그때만 회사명 · 사번 · 성명이 함께 있어야 해요.

적어 두면 좋아요 — 소속 · 전화 · 이메일

연락 수단이라 비어 있어도 발행은 그대로 진행돼요. 다만 장애 때 바로 닿을 수 있는 정보라, 허브 화면에서 나중에라도 채워 두면 좋습니다.

사번이 아니라 (회사명 + 사번)이 키예요

ITO 현장에는 원청·협력사 인원이 섞여 있어요. 사번만으로 키를 잡으면 회사가 다른 동일 사번이 한 사람으로 합쳐집니다. 유일 제약으로 그런 사고를 막아요.

담당 구분

publisher 올리기만 하는 사람 (기본) maintainer 유지보수 담당 owner 시스템 대표 담당자 — 허브 목록에 이 사람이 보여요

발행왜 저장과 조회를 나눴나

쓰기는 플러그인 안에, 읽기는 서버 한 곳에

저장이 서버 설치에 묶이면 곤란해요

대부분의 PC에는 조회 서버가 깔려 있지 않으니까요. 그래서 스키마와 버전 관리 로직을 플러그인 안에 넣었습니다 — 필요한 건 pip install sqlalchemy와 드라이버 하나뿐이에요.

엔진을 바꿔도 작업 방식은 같아요

테이블 정의가 한 곳에만 있고, SQLAlchemy가 엔진별 SQL로 알아서 컴파일해 줘요. MSSQL로 시작했다가 나중에 PostgreSQL로 옮겨도 .env 한 줄만 바꾸면 됩니다.

DB 설계담당자·권한을 더한 구조

기존 표는 그대로 두고, 사람 축을 옆에 붙였어요

DB 설계지금 무엇이 되고, 무엇이 남았나

표는 지금 만들어 두고, 강제는 스위치로 미뤘어요

권한을 나중에 한꺼번에 붙이려면 그때 스키마를 다시 흔들어야 하고, 그사이 쌓인 발행 기록에는 사람이 연결돼 있지 않아 소급도 안 됩니다. 그래서 자리를 먼저 만들어 두고 동작만 미뤄 뒀어요.

완료

1 · 사람을 남깁니다

발행할 때마다 담당자가 마스터에 쌓이고, 페이지 버전·발행 로그가 그 사람을 가리켜요. 지금 바로 동작합니다.

완료

2 · 역할과 권한 표

reader · editor · manager · admin 네 역할과 7개 권한이 자동으로 채워져요. 범위는 전체 / 시스템 / 레이어 3단으로 상속됩니다.

준비됨

3 · 부여와 회수

사번으로 사람을 찾아 역할을 줍니다. 회수할 때는 행을 지우지 않고 비활성으로 남겨 이력이 보존돼요. 스위치는 아직 off라 실제 차단은 일어나지 않습니다.

다음

4 · 로그인과 차단

조회 서버가 사내 SSO/LDAP로 사람을 식별하고, 스위치를 켜면 권한 없는 시스템은 목록에서부터 사라져요. 접근 시도는 감사 로그에 남습니다.

# 순서를 지킨다 — 부여를 끝낸 뒤에 켠다. 먼저 켜면 아무도 못 본다.
publish.py --grant "A123456=reader" --system-key ORDER
publish.py --list-grants ← 부여 현황 확인
publish.py --access-control on ← 마지막에, 사용자 확인 후
발행여러 명이 한 프로젝트를 나눠 맡을 때

한 사람이 분석하면 팀 전체가 그 결과를 받아요

토큰을 아끼는 지점

인덱스를 만드는 비용은 한 번만 내면 됩니다. 받은 사람은 --pull로 원래 경로에 그대로 복원하면, 영향도 분석·안전 변경을 바로 쓸 수 있어요.

받은 뒤엔 꼭 신선도를 확인하세요

build-index --check-stale 를 돌려요. 통과하면 그대로 쓰고, 어긋나면 증분 인덱싱 한 번(LLM 없이 수십 초)이면 맞춰집니다.

순서를 바꾸면 안 돼요

반드시 pull → check-stale 순서예요. 반대로 하면 방금 만든 로컬 인덱스를 오래된 DB 사본이 덮어써 버립니다.

바뀌는 것

매번 프로젝트를 설명하지 않아도 돼요. 컨벤션이 사람마다 갈리지 않고요. 영향 범위를 추측이 아니라 인덱스로 확인합니다. 담당자를 굳이 사람에게 묻지 않아도 되고요.

바뀌지 않는 것

승인과 배포는 그대로 사람의 몫이에요. HOLD·STOP에서 도구는 멈추고 이유를 말할 뿐, 스스로 밀어붙이지 않습니다.

솔직한 한계

WinForms Designer · DevExpress · XFDL · JSP/Struts XML 같은 대상은 PARTIAL 로 표시되고, 자동 변경 판정이 HOLD로 고정돼요. 위키의 "유지보수 지원 현황"에서 프로젝트별 상태를 먼저 확인하고 기대치를 맞추면 됩니다.
