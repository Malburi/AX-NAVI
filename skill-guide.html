1개요 — 스킬 구성과 3가지 호출 방식

플러그인 skills/ 폴더에는 24개 스킬이 있다. 워크플로우 스킬 17종 + 그중 자주 쓰는 7종을 짧게 부르는 별칭 7종이다. 플러그인만 설치하면 어느 프로젝트에서든 전부 활성화된다(단일 소스 구조 — 대상 프로젝트에 로컬 사본을 배포하지 않음).

호출 방식 3가지 — 전부 같은 스킬로 들어간다

방식예보장성
슬래시 (전체 이름)/ax-navi:safe-modify확정 경로 — 항상 그 스킬이 실행됨
짧은 별칭/modify 세션 만료 버그확정 경로 — 별칭이 즉시 해당 스킬로 위임
자연어 트리거"이거 고쳐줘", "어디서 쓰여?"LLM 확률 매칭 — 등록 문구와 가까울수록 안정적

자연어 트리거는 hook으로 강제되는 것이 아니라 LLM 판단 기반 확률 매칭이다(skill-triggers.html 2절). 반드시 특정 스킬을 태우려면 /modify·/ax-navi:safe-modify처럼 명시 호출한다.

2짧은 별칭 7종 & 한글 축약

긴 스킬명을 짧게 부르는 별칭. 별칭 스킬 자체는 얇은 위임 스텁으로, 인자를 그대로 대상 스킬에 넘긴다. Claude 기본 명령어(/init, /review 등)와 충돌하지 않게 명명됐고, 플러그인에 포함돼 있어 어느 PC에 설치해도 동일하게 동작한다.

2-1. 슬래시 별칭

별칭위임 대상하는 일
/modify [내용]safe-modify수정: 사전 영향분석 → 적용 → 사후 안전성 평가(GO/HOLD/STOP)
/impact [대상]analyze-impact변경 대상의 직간접 영향·위험도(1~10) 분석
/scaffold [기능명]scaffold-feature프로젝트 컨벤션 기반 신규 기능 스캐폴딩
/find [기능·키워드]find-feature관련 파일·클래스·메서드·SQL 목록 탐색
/flow [기능·API·화면]trace-logic진입점부터 DB/외부 시스템까지 흐름 추적
/sql [쿼리·SQL ID·DDL]review-sql사용처·성능·보안·트랜잭션·스키마 영향 종합 리뷰
/wikigenerate-wiki위키 페이지 세트 생성(call graph 시각화 포함)
별칭 이름 규칙 — 왜 /trace·/logic이 아닌가

harness-init이 대상 프로젝트마다 로컬 trace.md·find-logic.md 스킬을 배포하므로, 이름 충돌을 피해 흐름 추적은 /flow, 위치 탐색은 /find로 지었다.

3핵심 작업 스킬 8종 (일상 유지보수)

스킬별칭대표 트리거동작
safe-modify 수정 기본 경로/modify "수정해줘", "고쳐줘", "개선해줘", "버그 잡아줘", "이 패치 적용해도 돼?", "긴급 핫픽스", "GO/NO-GO?" 영향분석(impact-analyzer) → 변경 적용 → 패턴 적합성(pattern-conformance) + 로컬 검증(verify-target) + 안전성 평가(change-safety) → GO/HOLD/STOP 판정 → 인덱스·wiki 증분 갱신(GO 시 기본 실행, 허브 발행 이력 있으면 재발행 제안)
analyze-impact/impact "이거 수정하면 어디 영향?", "어디서 쓰이고 있어?", "이 함수 수정해도 돼?" 인덱스(call_graph·sql_usage·schema) 기반 직간접 영향 + 위험도 1~10 리포트. 수정·개발 작업의 시작점
scaffold-feature 개발 기본 경로/scaffold "개발해줘", "구현해줘", "코드 짜줘", "[기능명] 기능 추가", "패턴대로 만들어줘" .claude/patterns/ 컨벤션 로드 → 보일러플레이트 + 테스트 골격 생성 → 안티패턴 대조
vibe 게이트 생략— "알아서 해줘", "그냥 해줘", "바이브로", "빠르게 그냥 고쳐" 영향·안전 에이전트 생략, 패턴 선택·최소 실행 검증은 유지. DB 스키마/API 계약/트랜잭션/3+파일 변경이면 safe-modify·scaffold-feature로 자동 승격
trace-logic/flow "이 API 어떻게 처리돼?", "이 화면 저장 버튼 누르면 뭐가 실행돼?", "처리 흐름" logic-tracer 에이전트가 진입점→DB/외부까지 추적, 인덱스 trace 질의 우선
find-feature/find "결제 관련 파일 어디 있어?", "찾아줘", "담당 클래스" feature-finder 에이전트가 키워드로 파일·클래스·메서드·SQL 목록 반환
review-sql/sql "이 쿼리 성능", "N+1 확인", "인덱스 잘 쓰고 있어?", "DDL 영향 분석" sql-reviewer 에이전트가 사용처 역추적·인젝션·트랜잭션·락·스키마 영향 종합 리뷰. 조건부 스킬 — SQL 사용이 확인된 프로젝트일 때만 프로젝트 CLAUDE.md 표에 등록됨(스킬 자체는 항상 사용 가능)
plan-migration— "Spring Boot로 마이그레이션", "Oracle → PostgreSQL", "전환 계획", "리프트앤시프트" 인벤토리·매핑 테이블·단계별 계획·위험 등록부·테스트 전략·롤백 시나리오 생성. 조건부 스킬 — 대상 스택이 마이그레이션 후보일 때만 프로젝트 CLAUDE.md 표에 등록됨(스킬 자체는 항상 사용 가능)
safe-modify vs scaffold-feature vs vibe 분기

기존 코드 변경이면 safe-modify, 새 파일/기능 생성이면 scaffold-feature. 두 경로 다 게이트(영향분석·패턴·안전성)가 기본으로 붙는다. 게이트를 생략하는 vibe는 사용자가 "알아서/그냥/바이브"라고 명시적으로 말했을 때만 탄다.

6크로스리포(페어) 3종

백엔드·프론트엔드가 별도 저장소로 분리된 시스템용. pair-init으로 연동한 뒤 나머지 두 스킬이 활성화된다.

스킬대표 트리거동작
pair-init "백엔드 프론트엔드 연결해줘", "두 프로젝트 연동", "API 계약 추출해줘", "허브형 연동" 1:1(백+프론트) 또는 1:N(백+웹+모바일+관리자) 연동. api-bridge로 API 계약 추출·정합성 검증
cross-repo-scaffold "전체 스택 기능 만들어줘", "API부터 화면까지 만들어줘" 연동된 저장소 전체에 걸쳐 백엔드 API + 프론트 연동 코드를 한 번에 스캐폴딩
cross-repo-modify "양쪽 다 수정해줘", "이 API 바꾸는데 프론트 영향 있으면 같이" 한쪽 수정의 영향을 파트너 저장소까지 분석해 함께 반영

7프로젝트별 생성 스킬 플러그인 소속 아님

아래 스킬들은 플러그인 skills/에 없다 — harness-init 실행 시 writer가 대상 프로젝트의 실제 코드 기준으로 직접 작성해 그 프로젝트의 .claude/skills/에 배포한다. 내용(트리거 문구·예시 심볼·명령어)이 프로젝트마다 다르다.

로컬 스킬용도
trace.md그 프로젝트의 요청 흐름 추적 (실제 진입점·프레임워크 기준 예시 포함)
find-logic.mdSQL/테이블/인터페이스 ID/에러 메시지 → 담당 코드 역탐색
scaffolder.md그 프로젝트 구조 기준 신규 모듈 추가 체크리스트
cross-repo-scaffold.md / cross-repo-modify.mdpair 연동 시에만 생성 — 파트너 경로가 박힌 프로젝트 전용판
단일 소스 원칙 (2026-08-13부터)

정적 워크플로우 스킬 6종(analyze-impact/safe-modify/scaffold-feature/vibe/plan-migration/review-sql)은 프로젝트별로 달라질 내용이 없어 플러그인 전역판만 존재한다. harness-init은 이들의 이름을 프로젝트 CLAUDE.md 표·ito-guide.md에 등록만 하고 로컬 파일은 배포하지 않는다. 플러그인을 업데이트하면 모든 프로젝트에 즉시 반영된다.

9라우팅 설계 원칙

  • "개발해줘 / 구현해줘 / 새 기능" → scaffold-feature 컨벤션 기반 생성 · 기본값
  • "수정해줘 / 고쳐줘 / 개선해줘" → safe-modify 게이트 포함 · 기본값
  • "알아서 해줘 / 그냥 해줘 / 바이브로" → vibe 독립 에이전트 게이트 생략 · 명시적 opt-out
  • /modify · /ax-navi:<스킬명> → 해당 스킬 확정 경로 (유일한 보장 수단)
  • 기본값 = 게이트 경로. 범용 요청은 인덱스·패턴·안전성 평가를 태운다.
  • 게이트 생략은 opt-out 명시로만. 어떤 경로에서도 컨벤션 확인·최소 실행 검증(verify-target.mjs)은 생략하지 않는다.
  • 수정 스킬은 완료 후 build-index.mjs --mode incremental로 인덱스를, generate-wiki로 wiki를 함께 갱신해 다음 작업과 인수인계 문서가 최신 상태를 참조하게 한다.
